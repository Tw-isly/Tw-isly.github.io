这次写螺旋矩阵时，我先观察每一段应该走多远，再把规律写成循环。看到题解用两个方向数组统一处理移动，我觉得这个设计很巧妙，也产生了一个疑问：我是不是在用“数学思维”做题，而没有用上“计算机思维”？

重新梳理代码后，我更愿意把这次收获理解为：**发现规律已经是在设计算法，而把方向、位置和转弯条件表示清楚，可以让这个算法更容易实现、验证和复用。**

## 我的第一种思路：先找方向和步长的规律

题目要求从左上角开始，将 `1` 到 `n*n` 顺时针填入一个方阵。例如，`n = 4` 时：

```text
  1  2  3  4
 12 13 14  5
 11 16 15  6
 10  9  8  7
```

我的原代码先填好起点：

```cpp
int jz[10][10] = {0};
int i = 0, j = 0;
int sz = 1;
jz[0][0] = sz++;
```

之后把一次连续的直线移动看作一段，用 `k` 表示段号。方向按“右、下、左、上”循环，因此原代码用 `k % 4` 决定执行 `j++`、`i++`、`j--` 还是 `i--`。

这里 `i` 表示行，`j` 表示列：行号增加是向下，列号增加是向右。

步长的规律需要仔细区分。起点已经填过，所以第一段向右移动 `n-1` 次；随后向下和向左，也都移动 `n-1` 次。到第四段向上时，顶部已经填过，才缩短为 `n-2` 次。

以 `n = 4` 为例：

| 段号 `k` | 方向 | 移动次数 |
| --- | --- | --- |
| 1 | 右 | 3 |
| 2 | 下 | 3 |
| 3 | 左 | 3 |
| 4 | 上 | 2 |
| 5 | 右 | 2 |
| 6 | 下 | 1 |
| 7 | 左 | 1 |

因此，对 `n >= 2`，实际序列是 **前三段均为 `n-1`；若还有后续段，步长从 `n-2` 开始，每个正步长出现两次**。`n = 2` 时只有三段 `1, 1, 1`。不能直接写成从第一段起每两段递减。`n = 1` 时只有起点，没有实际移动。

把原代码中分散在各个分支里的步长计算提取出来，可以写成：

```cpp
for (int k = 1; k <= 2 * n - 1; ++k) {
    int steps = (k == 1) ? n - 1 : n - k / 2;
    // 在本段的方向上移动 steps 次，每次填入一个数字
}
```

这里的 `k / 2` 是整数除法。第一段单独处理，后面的相邻两段自然得到相同长度。对于 `n >= 2`，`2*n-1` 段的移动次数之和是 `n*n-1`，加上起点，正好填满方阵；对于 `n = 1`，循环中的步长为 0，同样不会多走。

我这份代码已经抽象出了两个规律：**方向每四段循环，步长按段号变化。**问题在于四个方向分支重复了相近的填数逻辑，改动时容易漏掉其中一处。

## dx/dy：把四种动作变成一张规则表

题解里的方向数组是：

```cpp
const int dx[4] = {0, 1, 0, -1};
const int dy[4] = {1, 0, -1, 0};
```

约定 `x` 表示行、`y` 表示列，`dir` 表示方向。两个数组在同一个下标上的元素，共同组成一次移动的坐标增量：

| `dir` | 方向 | `dx[dir]`：行变化 | `dy[dir]`：列变化 |
| --- | --- | --- | --- |
| 0 | 右 | 0 | 1 |
| 1 | 下 | 1 | 0 |
| 2 | 左 | 0 | -1 |
| 3 | 上 | -1 | 0 |

于是四种移动都可以写成同一段代码：

```cpp
x += dx[dir];
y += dy[dir];
```

顺时针转弯也只需要更新方向编号：

```cpp
dir = (dir + 1) % 4;
```

让我觉得巧妙的地方，是它把“向右时怎么写、向下时怎么写”变成了“当前方向对应什么数据”。循环负责统一执行移动，方向表负责描述移动规则。

这里使用 `const`，是为了让方向表的元素不能被普通赋值修改，也表达“这是一组固定规则”的意图。这一限制可以对照 [C++ 标准草案中的 const 规则](https://eel.is/c++draft/dcl.type.cv)。理解它时，不需要假定数组一定存放在某个特定内存区域。

## 保留数学推导，也能用上方向数组

方向数组和模拟并不是一套必须绑定使用的方案。`dx/dy` 解决的是“如何表示移动”，步长公式解决的是“这一段走多少次”。我原来的推导完全可以保留。

在已有的数组、起点和方向表基础上，原来四套循环可以合并为：

```cpp
for (int k = 1; k <= 2 * n - 1; ++k) {
    int steps = (k == 1) ? n - 1 : n - k / 2;
    int dir = (k - 1) % 4;

    for (int m = 0; m < steps; ++m) {
        i += dx[dir];
        j += dy[dir];
        jz[i][j] = sz++;
    }
}
```

这个版本仍然依赖我推导出的方阵步长规律，但消除了四个方向分支里的重复逻辑。学到一种新抽象后，可以先用它改进自己的方案，再考虑是否需要换掉整个算法。

## 第二种思路：记录状态，判断下一格能不能走

逐格模拟时，可以不预先计算每段的长度。程序只需要记录当前行列、当前方向，以及哪些格子已经填过。

每次填入一个数字后，计算下一格。如果下一格越界或已经填过，就顺时针转弯，再计算下一格。这里用 `0` 表示未填，数字从 `1` 开始，因此矩阵本身就能记录访问状态。

下面是一份完整写法。为了与我原来的 `10 × 10` 数组保持一致，输入范围限定为 `1 <= n <= 10`：

```cpp
#include <iomanip>
#include <iostream>

int main() {
    int n;
    if (!(std::cin >> n) || n < 1 || n > 10) {
        return 0;
    }

    int a[10][10] = {0};
    const int dx[4] = {0, 1, 0, -1};
    const int dy[4] = {1, 0, -1, 0};
    int x = 0, y = 0, dir = 0;

    for (int value = 1; value <= n * n; ++value) {
        a[x][y] = value;
        if (value == n * n) {
            break;  // 最后一个数字填完，不再移动
        }

        int nx = x + dx[dir];
        int ny = y + dy[dir];
        bool canMove = nx >= 0 && nx < n &&
                       ny >= 0 && ny < n && a[nx][ny] == 0;

        if (!canMove) {
            dir = (dir + 1) % 4;
            nx = x + dx[dir];
            ny = y + dy[dir];
        }

        x = nx;
        y = ny;
    }

    for (int i = 0; i < n; ++i) {
        for (int j = 0; j < n; ++j) {
            std::cout << std::setw(3) << a[i][j];
        }
        std::cout << '\n';
    }
}
```

边界判断写在访问 `a[nx][ny]` 之前，是因为内置 `&&` 会从左向右短路求值：前面的条件不成立，后面的数组访问就不会执行。这个行为由 [C++ 标准草案中的逻辑与规则](https://eel.is/c++draft/expr.log.and)规定。

“不能直走时只转一次，就有合法下一格”依赖本题的条件：完整的无障碍方阵、从左上角开始、顺时针向内填充，并且最后一格填完后停止。如果加入任意障碍，这个前提就可能失效，需要重新设计转向、搜索和终止规则。

## 特殊规律与状态模拟，区别在哪里？

| 比较点 | 按步长规律生成 | 根据状态逐格模拟 |
| --- | --- | --- |
| 核心问题 | 第 `k` 段应该走多少步？ | 当前方向的下一格能不能走？ |
| 决策依据 | 段号、方向周期、步长公式 | 当前位置、方向、边界和访问状态 |
| 验证重点 | 公式、首段特例、总步数 | 判断顺序、转弯条件、停止时机 |
| 题目变化时 | 重新推导适用的长度规律 | 调整状态和移动规则，必要时更换算法 |

这两种写法都要填入 `n*n` 个数字，时间复杂度都是 `O(n²)`。若按输入规模分配并保存整个矩阵，空间复杂度也都是 `O(n²)`；上面的示例固定使用 100 个整数，只面向 `n <= 10`。方向表只占常数空间。

因此，这次重构的主要收获是减少重复、明确状态与规则，而不是改变填满矩阵的时间复杂度。公式方法在规则明确时很直接；状态模拟则把判断集中到“下一步是否合法”，往往更方便表达过程。哪种更合适，取决于题目条件。

方向数组的表示方式也能复用于网格邻居枚举、迷宫搜索和 BFS，但这些问题还需要各自的搜索策略与访问规则。复用的是移动的表达方式，不是螺旋矩阵的完整解法。

## 我想带到下一道题里的习惯

我原先担心自己过于依赖数学推导。现在看来，推导让我抓住了方向周期和长度规律；状态抽象则让我看清，程序每一步究竟需要知道什么、检查什么、更新什么。

以后遇到类似问题，我想多做三件事：

1. **用小样例核对规律。**例如 `n = 1、2、3、4`，既检查单格边界，也检查奇偶大小和转弯过程。
2. **找出重复动作背后的数据。**四个方向都在“移动并填数”，变化的只是坐标增量，就可以提取成方向表。
3. **说清状态和成立条件。**哪些变量决定下一步？哪些格子允许进入？什么时候结束？转一次就能走的依据是什么？

这次最值得留下的，并不只是 `dx/dy` 这几行代码，而是一次思考上的推进：从“我找到了一个能生成答案的规律”，走到“我能把规律、状态和操作分别表示清楚，并解释程序为什么始终正确”。
